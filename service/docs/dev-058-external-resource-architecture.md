# DEV-058 – Architecture decision: deduplicated external model resources

## Accepted target

Blender Workspace will use **option B** for new textured revisions: native
BLEND geometry and material bindings plus a revision-scoped, immutable resource
manifest that names SHA-256-addressed external resources. Unlike the previous
proposal, this does not require retaining an embedded copy of every texture
inside every revision. Project-specific revisions and render jobs must resolve
their own manifest, not trust arbitrary hashes supplied by the browser or MCP.

This change is intentionally **not a second public file API**. A content hash
is an identifier, never a sufficient authorization credential.

## Storage foundation (this PR)

`ContentAddressedResourceStore` stores a verified file at

```
<private-volume>/.resources/sha256/<first-two-hex>/<64-char-sha256>
```

The bytes are staged in the destination shard and linked atomically to their
final immutable name. Matching bytes are stored once even across concurrent
calls and independent repository revisions. An existing blob is validated,
never overwritten. The store exposes `put(sourcePath)` and
`verifiedPath({sha256,sizeBytes})` solely to trusted internal callers.
Resource garbage collection is **disabled** until a correct reference graph,
project-deletion policy and quarantine/grace period are implemented. This
chooses possible temporary extra storage over prematurely deleting a texture
that is still needed by a saved revision or an in-flight rendering.

## Invariants for full option-B rollout (next implementation step)

1. **Revision publishing is atomic:** a revision may become visible only when
   every required resource has been persisted and checksum-verified. The
   revision manifest has exact logical relative paths, content hashes,
   sizes and resource categories; unsafe paths, duplicates and symlinks fail.
2. **Blender native scene:** rewrite supported texture filepaths to stable
   logical resource names inside an isolated working directory and save a
   native BLEND *without embedding duplicate texture bytes*. External data
   that cannot be inventoried or safely reproduced makes the revision
   non-publishable; no silently degraded rendering.
3. **Modeling and rendering:** materialize all referenced resources from the
   manifest into the temporary job directory, then open the BLEND with
   relative paths repaired in the isolated Blender worker. Missing/corrupt
   resources must fail before the billable Modal job is started whenever
   feasible.
4. **Native download:** portable `.blend` is generated by restoring and
   packing the manifest-defined resources, or `.zip` contains the native
   scene, resources and manifest. Both owner and public downloads use the
   same packaging code. No public hash-only resource endpoints.
5. **Project export/import:** archives contain all unique content-addressed
   resources once, retain revision-to-resource associations and validate
   complete reconstruction before accepting import.
6. **Lifetime:** deleting an uploaded source does not remove data needed by
   revision manifests. Cleanup uses exact references plus protections for
   concurrent jobs, imports, interrupted publishing and recovery.
7. **Compatibility:** no need to preserve experimental textured-revision
   behavior. Untextured revision, preview, rendering and download flows remain
   supported. Existing stored BLEND files remain valid until explicitly
   migrated; do not rewrite immutable revisions in place.

## Important current limitation

**This PR is only the safe storage foundation.** It does not change the
active Blender worker's `pack_all`, revision manifests, rendering contracts
or export routes yet. New external-only revision publication must not be
enabled before the end-to-end pipeline and its tests are merged. Therefore
the current downloadable BLEND behavior remains unchanged on this branch.

## Validation

Node tests cover simultaneous ingestion of identical bytes, persistent
deduplication, new hashes for modified textures, corruption rejection,
symlink rejection and invalid resource identifiers. The service's TypeScript
build and all repository-required CI workflows must pass before merge.
